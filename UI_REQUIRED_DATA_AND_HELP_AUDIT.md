## 2. Определение обязательности

Базовый сигнал — `min_occurs > 0` структуры или `field_usage: REQUIRED` выбранного сообщения. GUI считает поле безусловно обязательным только тогда, когда вся цепочка родителей также обязательна и для поля нет условной политики. Дополнительно минимальное заполнение учитывает безусловные исполняемые правила `cardinality` с положительным минимумом, относящиеся к текущей структуре. Для кратности `1..*` создаётся один структурный экземпляр. Условные правила, фильтрованная кратность, сравнения и внешние классификаторы не заменяются догадками.

## 3. Кнопка «Обязательные данные»

Использует тот же `TestDataGenerator` в режиме `required`; вносит только отсутствующие значения и не заменяет пользовательский ввод. Код сообщения берётся из выбранного MSG, код документа — из назначенной ему структуры. Если для обязательного поля нужен отсутствующий локально классификатор, поле остаётся пустым, а уведомление сообщает о необходимости подтверждённого значения. При повторном нажатии существующие экземпляры не дублируются. Сохранение черновика и «Создать XML» остались справа.

## 4. «Тестовые данные»

Существующий режим генератора сохранён. Он по-прежнему создаёт расширенный тестовый набор и удовлетворяет поддерживаемым исполняемым правилам. Для `UniversallyUniqueIdType` теперь создаётся UUID вместо строки `TEST`.

## 5. Справка и примеры

Справка строится одним renderer из названия, назначения, инструкции ввода, примера, формата и обязательности. Технические сведения идут после основного текста. Для кода страны учтён контекст адреса, патентного ведомства и участника. Примеры выбираются в порядке: фиксированное значение, допустимое локальное значение, существующий пример политики, проверенный пример типа, проверенный пример regex. При недостатке нормативных данных показывается честное сообщение об отсутствии безопасного примера. Пустые описания получают явную осторожную подсказку без приписывания нормативного смысла.
